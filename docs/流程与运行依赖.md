# hg19 WXS/WGS 胚系流程：分析步骤与运行依赖

本文对应根目录 `workflow.wdl` 的当前初版。入口为 WDL 1.0 workflow `WxsGermlineHg19`，由 Cromwell 执行；Choppy 的 `defaults`、`inputs`、`schema.json`、`manifest.json` 用于提交端配置。代码布局沿用上游 GitHub 仓库的主 WDL + `tasks/*.wdl` 形式，任务内调用 Shell 命令，`scripts/*.py` 只处理 BED 与交付元数据。

## 1. 输入与适用范围

| 类别 | 必需输入 | 含义 |
| --- | --- | --- |
| 样本 | `sample_id`、`library_id`、`platform` | 单受检者；进入 BAM read group。当前同一提交共用一个 library ID |
| 测序 | `fastq_r1`、`fastq_r2` | 上游已合并的单对 R1/R2 FASTQ，均为单个 `File`，本流程不再按 lane 拆分或合并 |
| 分析模式与捕获范围 | 可选 `capture_bed`、`capture_padding` | 有 BED 时为 WXS，按实际捕获范围调用并默认 padding 100 bp；省略或 `null` 时为 WGS，从 FAI 取全长主染色体，忽略 padding |
| 性染色体组成 | `sex_chromosome_complement` | `XX`、`XY` 或 `UNKNOWN`；须依据已确认的样本信息设置，默认 `UNKNOWN` 不调用 X/Y |
| 可选检测范围 | `target_bed` | 仅启动下游范围核查和区域派生；不改变比对、BQSR 或主 gVCF |
| 参考 | `ref_fasta`、`ref_fai`、`ref_dict`、`bwa_index_files[]` | 必须来自同一 hg19 UCSC FASTA；BWA 索引顺序为 `.amb/.ann/.bwt/.pac/.sa` |
| BQSR 已知位点 | `dbsnp_vcf/index`、`mills_vcf/index` | 用作 BaseRecalibrator known-sites，不作受检者 GT 真值 |
| 辅助代码 | `intervals_script`、`delivery_script` | 指向本仓库 `scripts/intervals.py`、`scripts/delivery.py` 的可本地化路径 |

`defaults` 中的 OSS 路径来自上游资源命名，其中 FAI、字典、BWA 索引和 VCF `.idx` 的具体对象名尚未连接 OSS 核对。部署前要确认所有对象存在、contig 名称和长度一致、VCF REF 与 FASTA 一致，并记录版本和校验和。可选的 `capture_bed` 与 `target_bed` 应从 Cromwell JSON 省略或设为 `null`；空字符串不是有效 `File`。Choppy 模板在 capture BED 未填写时不输出该键。历史 `bed_file` 只能由提交适配层映射为 `capture_bed`，若两个字段冲突则拒绝提交。

始终对 `chr1`–`chr22` 运行 HaplotypeCaller。WXS 的捕获 BED 必须含常染色体区间；WGS 则要求 FAI 存在 `chr1`–`chr22`、`chrX`、`chrY`、`chrM`，并分析各适用 contig 的全长。设置 `XX` 时额外以二倍体调用 chrX 并排除 chrY；设置 `XY` 时 chrX PAR 为二倍体，chrX 非 PAR 和 chrY 非 PAR 为单倍体，chrY PAR 明确排除。跨越 chrY PAR 边界的区间仅将 PAR 片段写入排除清单。`UNKNOWN` 时 X/Y 均排除，WGS 也不会凭覆盖率推断倍性。WXS 的 `capture_bed` 含 `chrM` 或进入 WGS 时，独立运行 Mutect2 mitochondrial mode 和 FilterMutectCalls。该参考必须是 [16,571 bp 的 hg19 UCSC chrM](https://genome.ucsc.edu/cgi-bin/hgTracks?db=hg19&position=chrM)，不可混用 16,569 bp 的 rCRS/GRCh37 chrMT 坐标；其他参考 contig 写入排除清单。非 XX/XY 核型、CNV、STR、HLA、扩增子和 UMI 文库的专用处理尚未实现。

## 2. 数据如何流转

```text
已合并的 R1/R2 → fastp → 修剪后 FASTQ + HTML/JSON
                            ├─ FastQC → 修剪后读段 QC
                            └─ BWA-MEM（样本级 RG）→ samtools sort/index → GATK MarkDuplicatesSpark
                                     ↓
capture_bed 存在 → WXS 坐标校验、padding ┐
capture_bed 省略 → WGS FAI 主染色体全长 ┴→ PAR 拆分 → 常染色体、X/Y、chrM 分区 BED
                                     ↓
              GATK BaseRecalibrator（常染色体及启用 X/Y 分区内训练）
                         ↓
              GATK ApplyBQSR（完整 BAM）→ recal BAM/BAI
                         ├─ Qualimap BAM QC
                         └─ HaplotypeCaller -ERC GVCF（各分区按倍性分别运行）
                                      ├─ 常染色体原生 sample.g.vcf.gz + .tbi
                                      └─ 适用的 X/Y 分区 gVCF + .tbi
                         └─ chrM: Mutect2 mitochondrial mode → FilterMutectCalls
                                      └─ 候选变异 VCF + .tbi（中间结果）
target_bed 存在时：
  target_bed + 各调用分区 → 范围内/部分重叠/范围外状态
                          ├─ 核基因组有范围内区间：GenotypeGVCFs --include-non-variant-sites
                          │   → 各分区 target_regions.all_sites.vcf.gz + .tbi（中间结果）
                          └─ chrM 有范围内区间：SelectVariants → 变异子集 VCF + .tbi
```

### 2.1 预处理

`ValidateInputs` 检查两个 FASTQ 非空、read group 标识和 BWA 索引数量。`TrimReads` 对已合并的 R1/R2 运行一次 fastp；`Fastqc` 检查修剪后的双端 FASTQ。`AlignReads` 使用完整 hg19 FASTA 比对，在样本级 RG 中记录 `ID=sample_id`、`SM=sample_id`、`LB=library_id`、`PL=platform`，不编造 lane 或 PU，再排序和建索引。`MarkDuplicates` 标记重复读段并保存 metrics，不物理删除 reads。上游合并 FASTQ 的方法和来源应由样本交接记录保存。

### 2.2 捕获范围、BQSR 与 gVCF

`PrepareCapture` 在 WXS 模式依据 FAI 校验 BED 坐标，在 WGS 模式从 FAI 生成主染色体全长范围；两种模式都按参考顺序生成独立分区、总 `analysis_intervals.bed` 和不含 chrM 的 `bqsr_intervals.bed`。`BaseRecalibrate` 在 BQSR 范围内结合 dbSNP/Mills 估计校准表；`ApplyRecalibration` 对完整标记重复 BAM 应用 BQSR，保留后续复核所需读段。`HaplotypeGvcf` 对常染色体和适用的性染色体分区分别运行 GATK HaplotypeCaller `-ERC GVCF`，保留原生参考块、`<NON_REF>`、变异记录和索引。常染色体主 gVCF 不做 PASS-only 筛选或 ANNOVAR 改写，性染色体分区 gVCF 不伪装成已合并文件。

`MitochondrialVariants` 对选定范围内 chrM 从同一 recal BAM 运行 Mutect2 mitochondrial mode 与 FilterMutectCalls，保存未过滤 VCF、Mutect stats、带 FILTER 标记的 VCF 和索引，不做 PASS-only 删除。chrM 为环状基因组，本初版未做断点移位重比对；NuMT、覆盖率与异质性阈值尚未经 WXS/WGS 样本验证。线粒体 VCF 是候选变异记录，未输出位点不表示参考型。方法选择参考 [GATK 线粒体流程](https://gatk.broadinstitute.org/hc/en-us/articles/4403870837275-Mitochondrial-short-variant-discovery-SNVs-Indels)，但本流程没有实现其全部步骤。

gVCF 的参考块不等于逐碱基最终报告记录。块内某个位置的精确深度、目标等位基因和可报告性不能仅凭块首字段推断。`MakeDelivery` 做基础格式与文件检查，记录哈希和运行范围信息；当前 `ready_for_import_test` 与 `ready_for_report` 均为 `false`。

### 2.3 可选目标 BED 分支

`PrepareTargets` 核对目标 BED 与各调用分区，保留 `InScope`、`PartiallyInScope`、`OutOfAnalysisScope`、`ComplementUnspecified`、`AbsentInXX`、`ParOnYExcluded`、`UnsupportedContig` 等状态。WXS 的 `outside_capture` 说明目标是否完全落在原始捕获 BED 内，WGS 为 `not_applicable`。核基因组范围内目标由 `GenotypeTargetRegions` 从对应 gVCF 派生包含非变异位置的区域 VCF。chrM 范围内目标由 `SelectMtTargetVariants` 从带 FILTER 标记的 VCF 提取变异子集，不包含参考型位点。两类文件只供接入和算法验证；当前没有事件级 REF/ALT manifest、跨界 Indel 复核、逐位点证据屏蔽及完整 no-call 导出，因此不能当成最终目标检测 VCF。没有范围内目标的分区派生 VCF 为 null，范围状态 TSV 仍输出。

### 3.2 检查容器内软件、包和路径

先按镜像逐个设置 `$image`，使用 `--entrypoint /bin/sh` 绕过镜像默认入口进行检查；`--pull=never` 保证检验的是刚拉取并记录的本地镜像。`command -v` 给出 `PATH` 中的入口，`readlink -f` 给出解析后的真实文件，二者都应记录。下面以 `analysis_image` 为例：

```powershell
$image = 'crpi-xvcezojsbq275htp.cn-shanghai.personal.cr.aliyuncs.com/nap_hub/sentieon-replaced:2.0'
docker image inspect $image --format 'Entrypoint={{json .Config.Entrypoint}} Cmd={{json .Config.Cmd}} Env={{json .Config.Env}}'
docker run --rm --pull=never --entrypoint /bin/sh $image -ec 'echo "PATH=$PATH"; for x in sh bash ln test bwa samtools gatk; do command -v "$x" || exit 1; done; for x in bwa samtools gatk; do p=$(command -v "$x"); echo "entry=$p"; if command -v readlink >/dev/null 2>&1; then readlink -f "$p"; fi; done; samtools --version; gatk --version; bwa 2>&1 || true'
```

`bwa` 无参数时通常返回非零；最后一项只用来查看版本/用法，不能据此判定失败。对其余镜像重复同样的 `docker run`，将必需程序替换为下表，并对关键命令取版本、帮助或执行小样本：

| 镜像参数 | `command -v` 必查项 | 版本/功能必查项 |
| --- | --- | --- |
| `fastp_image` | `fastp`、`sh`、`bash` | `fastp --version`；用一对短 FASTQ 生成 JSON/HTML |
| `fastqc_image` | `fastqc`、`sh`、`bash` | `fastqc --version`；对短 FASTQ 输出 HTML |
| `analysis_image` | `bwa`、`samtools`、`gatk`、`sh`、`bash` | `samtools --version`、`gatk --version`；小 FASTQ 完成 BWA → sort/index → MarkDuplicatesSpark → index |
| `gatk_image` | `gatk`、`samtools`、`sh`、`bash` | `gatk --version`、`samtools --version`；检查所有 8 个本流程 GATK 子命令及 `--sample-ploidy`、`--include-non-variant-sites`、`--mitochondria-mode`，再用小数据执行 BQSR、gVCF、chrM 分支 |
| `qualimap_image` | `qualimap`、`awk`、`tar`、`java`、`sh`、`bash` | `java -version`、`qualimap --help`；小 BAM 分别试有/无 `-gff` 的 `bamqc`，确认 PDF/HTML 与归档可生成 |
| `python_image` | `python3`、`sh`、`bash` | `python3 --version`；`python3 -c 'import argparse,csv,hashlib,json,pathlib'`；用挂载的 `scripts/intervals.py`、`scripts/delivery.py` 试 `--help` |

示例：`docker run --rm --pull=never --entrypoint /bin/sh $image -ec 'command -v gatk; gatk GenotypeGVCFs --help'`。把 `$image` 换成当前检查的镜像；所需子命令和选项以 `tasks/*.wdl` 为准，帮助文本仅是静态检查，必须再做小数据运行。若 `/bin/sh`、`bash` 或工具入口不存在，应视为该标签与当前任务不兼容，而不是只改 PATH 就默认通过。`gatk_image` 缺 `samtools` 时，当前 `ApplyRecalibration` 会在 `samtools index` 失败；`analysis_image` 缺 `gatk` 时 `MarkDuplicates` 会失败。替代镜像必须同时满足该参数下所有任务，不可只验证镜像名。

如需确认**包来源与依赖库**，在对应容器内先看 `command -v dpkg-query`、`command -v rpm`、`command -v python3`。Debian/Ubuntu 镜像可对真实二进制路径执行 `dpkg-query -S /实际/路径`、`dpkg-query -W`；RPM 镜像可用 `rpm -qf /实际/路径`、`rpm -qa`；Python 镜像可用 `python3 -m pip list --format=freeze`。例如已设置 `$image` 时：

```powershell
docker run --rm --pull=never --entrypoint /bin/sh $image -ec 'p=$(command -v samtools); echo "executable=$p"; if command -v readlink >/dev/null 2>&1; then p=$(readlink -f "$p"); echo "resolved=$p"; fi; if command -v dpkg-query >/dev/null 2>&1; then dpkg-query -S "$p" || true; dpkg-query -W samtools || true; elif command -v rpm >/dev/null 2>&1; then rpm -qf "$p" || true; fi; if command -v ldd >/dev/null 2>&1; then ldd "$p" || true; fi'
```

在包含 `samtools` 的镜像上运行上例；其他镜像把程序名换成该镜像必查项。`ldd` 可帮助发现缺失的动态库；对 Shell 脚本或包装器应先看首行和实际调用的可执行文件，不要把脚本直接交给 `ldd`。部分工具是手动安装的脚本或 JAR，未登记为系统包；此时记录 `readlink -f`、脚本首行/JAR 文件路径、工具自身版本即可，不能因包管理器没有记录就认定程序不存在。不要在生产镜像内临时安装依赖来通过验收，应构建并固定新镜像。

把每张镜像的拉取结果、平台/digest、入口与 PATH、程序及真实路径、版本、包清单、GATK 子命令检查和最小任务运行日志归档；这也是后续端到端验证前的镜像验收记录。Windows shell 中未发现 Docker/Java 可执行文件；Ubuntu-24.04 WSL 已有 Java 21 和下述 WDL 校验工具，但**六张镜像仍未通过拉取或容器内检查**。[Docker pull](https://docs.docker.com/reference/cli/docker/image/pull/)、[run](https://docs.docker.com/reference/cli/docker/container/run/)、[image inspect](https://docs.docker.com/reference/cli/docker/image/inspect/) 可作为命令参考。

本机 WSL 公共目录 `/opt/cromwell/81/` 安装了官方 Cromwell 81 (`cromwell-81.jar`，SHA-256 `c298cc7883decac906863c14b980fd61b75e746a1058fd77a464e2adb370aeca`) 和 WOMtool 81 (`womtool-81.jar`，SHA-256 `7958d97715cb2b8d90532e3cf5338a47bfc8199ad6661d29c287f107d1653e43`)；目录/文件权限允许普通 WSL 用户读取。Windows Codex 执行 `& .\scripts\validate_wdl_wsl.ps1`，脚本将仓库 WDL 路径转换为 WSL 路径并运行 WOMtool；WSL 中可直接运行 `java -jar /opt/cromwell/81/womtool-81.jar validate workflow.wdl`。2026-10-22 检查返回 `Success!`，`validate -l` 列出全部 15 个 task imports。这是语法、导入和类型语义检查，不执行分析任务。

## 4. 交付文件与验收边界

| 输出 | 用途 |
| --- | --- |
| `gvcf`、`gvcf_index`，可选 X/Y 分区 gVCF/索引 | 原生 GATK gVCF 和 `.tbi`，用于报告系统接入测试与后续派生；分区文件未合并 |
| 可选 `mt_unfiltered_vcf`、`mt_mutect_stats`、`mt_vcf`、`mt_vcf_index` | chrM 候选变异与过滤中间结果，在 WXS 捕获 BED 含 chrM 或 WGS 模式下输出 |
| `analysis_intervals_bed`、`bqsr_intervals_bed`、各分区 BED、`excluded_capture_intervals_tsv` | 声明实际调用、BQSR 训练和排除区间；WGS 的分析范围由 FAI 推导 |
| `recalibrated_bam`、`recalibrated_bam_index` | 保留读段证据，供复核和后续补分析 |
| `fastp_report`、`fastp_html_report`、`fastqc_reports`、`duplicate_metrics`、`qualimap_report` | 预处理与 BAM 质量检查材料 |
| `sample_qc_json`、`run_manifest_json` | 当前基础预检、`analysis_mode`、文件哈希和范围声明；未达到最终报告门禁 |
| 可选 `target_scope_tsv`、`target_in_scope_bed` | 请求目标与实际调用范围的关系 |
| 可选核基因组各分区 `target_regions_all_sites_vcf`、索引 | GATK 原始区域派生结果，仅为中间文件 |
| 可选 `mt_target_regions_vcf`、索引 | chrM 带 FILTER 标记的变异子集，不是 all-sites 文件 |

当前已用合成 BED/VCF 测试辅助脚本与 XX/XY、PAR 边界、chrM 范围状态；本地 WSL WOMtool 81 已校验主 WDL 及全部 imports。目标 Choppy/Cromwell 后端仍需验证输入类型、ZIP 提交、runtime 配置及实际执行，再用真实样本验证每个镜像和 OSS 对象，特别是性染色体倍性、同源区域、线粒体断点/NuMT/异质性和索引查询。正式报告放行还需目标清单、逐位点 QC、样本身份与正交验证；现阶段不能据此出具风险结论。

## 5. 提交与复核

1. 确认 `defaults` 中的 OSS 资源、镜像、实例类型和两个脚本路径；本地执行可从 `inputs.example.json` 复制为被忽略的 `inputs.json` 并替换路径。
2. Choppy 模板 `inputs` 接收单对已合并的 R1/R2，渲染后先检查 JSON；`capture_bed` 未提供时不输出该键并按 WGS 运行，`target_bed` 未提供时也不输出该键。
3. 编辑 WDL 后先在 Windows Codex 运行 `& .\scripts\validate_wdl_wsl.ps1`，或在 WSL 运行 `java -jar /opt/cromwell/81/womtool-81.jar validate workflow.wdl`。提交真实小样本前，用 `python3 -m zipfile -c imports.zip tasks` 打包依赖，并在目标后端以 `java -jar /opt/cromwell/81/cromwell-81.jar run workflow.wdl --inputs inputs.json --imports imports.zip --metadata-output metadata.json` 运行（若后端不是本机 WSL，应使用后端自己的 Cromwell JAR 路径）。Choppy 服务模式须提交等价的 `workflowDependencies` ZIP。分别测试有/无 `capture_bed` 的 WXS/WGS，以及有/无 `target_bed`；同一模式下目标 BED 不应改变主 gVCF 的分析范围。Cromwell 的 `run` 参数和 ZIP 路径布局见 [官方命令行](https://cromwell.readthedocs.io/en/latest/CommandLine/) 与 [Imports](https://cromwell.readthedocs.io/en/stable/Imports/)。
4. 复核输出 header、样本 ID、gVCF 参考块、索引查询、排除区间、目标范围外状态和 QC；记录真实镜像 digest、参考哈希、运行 ID 及问题。
